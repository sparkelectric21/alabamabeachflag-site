Incident guide

Emergency response

When safety data may be wrong, unavailable is safer than a fabricated or unverified status.

Provider HealthVerificationPublic configurationPublic beach conditionsPublic v2 flagsAnnouncements
With CodexInvestigate, recommend, verify
  1. Confirm the issue in Provider Health, Verification, public API output, and the official source.
  2. Ask Codex to inspect current production state and recommend the narrowest safe control. Do not authorize code changes or deployment.
  3. Use monitor only first when uncertainty remains and safety is not immediately at risk; disable data known or reasonably believed unsafe or misleading.
  4. Confirm APIs, providers, beaches, app, widget, cache, and old-client impact; then apply through this console.
  5. Refresh until protected and public revisions match. Verify the public API, app, and widgets.
  6. Add an announcement separately if communication is needed.
  7. Gather fresh recovery evidence; restore only after verification, then review the audit record and document the incident.
Without CodexPhone and browser checklist
  1. Check the official source, Provider Health, and Verification.
  2. Inspect current control state and choose the narrowest control.
  3. Choose monitor only or disabled; select a reason code and write a clear operator reason.
  4. Select a short duration and prefer review-required expiry.
  5. Review affected APIs, providers, beaches, app, widget, cache, and old-client impact.
  6. Enter typed confirmation when required and apply the change.
  7. Refresh until protected and public revisions match; check the public API, app, and widgets.
  8. Add a separate announcement when needed. Record incident ID and evidence.
  9. Restore only after fresh evidence. Confirm audit history records the full sequence.
